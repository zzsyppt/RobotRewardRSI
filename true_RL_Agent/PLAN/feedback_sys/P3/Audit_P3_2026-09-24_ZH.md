1. **从原始数据到词条的翻译是正确的。** Stair 参考策略 864 回合、312,387 个事件，以及 Push velocity 240 个恢复单元、force 192 个锚点，用独立的 numpy 实现逐项重算，与交付结果完全一致（§2）。词典里没有发现定义错误或实现错误；P2 已确认的两条语义边界（历史槽不是子步时序、注入步帧为注入前）在 P3 的定义与实现中都被正确遵守。
2. **可以开启人工评测。** 53 项材料、rubric、空评分表、完整真值、共同父本与 4 张派生时间轴齐全，评阅 ZIP 不含臂名映射，48/48 终态与 92 个账本槽已由用户根复核（§5）。评测结果应解读为"这一版 8 KiB / 12 KiB 工作集配置"的收益，而非行为表达思想本身的上限，原因见第 3 条。
3. **三个不阻断评测、但应在下一阶段前决定的工程问题**（§3、§4）：

### 2.3 语义提醒（不是错误）

- **"slip" 主要是接触沿的瞬变。** 46,092 个 slip_body 事件中，与触地沿重合 13,392、与离地沿重合 18,566、两者都重合 7,801，只有 6,333（13.7%）落在支撑期内；中位长度 1 步，达到 5 步确认的只有 2,282（5.0%）。画像里"确认前"的 slip 列使用 5 步 streak，是有意义的；但 `window_slip_any` 无 streak 要求，在所有 24 行里都≈n（成功行 108/108、55/55…），没有区分度却占字节。真实父子差分（fca→Gen8，`results/stair_parent_gen8_diff_r2.json`）里这一点更明显：确认 slip 率在 c0_id 从 108/108 降到 1/108，而 window 列两边都是 108/108。
- **停滞在时间线里不可见。** r1.e48（作者看到的 timeout 例子）原始数据：最后 8 s 里 RR 足接触力恒为 0、离平台面 2.4 cm、x=0.53 m（第一级立面在 0.75 m），前两足在第一级踏面（x 0.85/0.90），根部静止。词表能表达的只有 `low_progress`；`contact_instant` 区间被排除在时间线之外，又没有"非接触且静止"的词条，所以作者看到的 5 个事件里 4 个是 2 s 以前的抬足。全档有 36 个回合出现某足连续≥2 s 非接触，集中在倾覆与停滞两类失败。这是覆盖缺口，不是错误。
- **Push 方向样本**取窗口末帧，见 §3.3。

### 2.4 关于视觉确认

本次用原始数组的派生图完成核对（`stair_r1_e48_raw.png` 与用户的 4 张时间轴一致），没有在服务器启动 Isaac 渲染。理由：词条的定义都是可从存档数值判定的量，渲染只能回答"接触的是台阶哪一部位"这类词表明确声明不表达的问题；P6 之前不建媒体链路是主计划的决定。若后续要为 P6 选取录制池，r1.e48 型停滞和 c2 粗糙面上的 low_clearance 是最值得录的两类。

## 3. 信息量与成本

### 3.1 封存时重算在 GPU 租约内

| 运行 | 租约 (s) | rollout+聚合 (s) | 档案 manifest 写完 → 回执封存 (s) |
|---|---:|---:|---:|
| P2 `stair_parent_on`（864 回合，采集开） | 271.2 | 251.8 | 1.4 |
| P3 `stair_v3_reference_r2_on` | 675.8 | 284.2 | — |
| P3 `stair_v3_reference_r5_on` | 749.4 | 286.6 | 379.5 |

`build_stair_eval_phase_summary` 在评估进程内调用 `build_stair_behavior`，后者用 `recompute_stair_numeric_evidence` 重新读取并解码刚写好的 73 MB 档案，再逐步逐足跑纯 Python 的 `_Episode.observe`（同一派生我的 numpy 实现只需 28.5 s，用户离线派生 214 s）。这一步发生在 Isaac 进程退出之前，所以 GPU 租约多占约 380 s，是 rollout 本身的 1.3 倍。P3 本阶段 5 次运行合计 0.62 GPUh，其中约 0.3 GPUh 是这个重算。进入正式搜索后每个候选的 public-dev 评估都会付这笔钱。Push 的对应重算 <1 s，无此问题。

两种不改变"行为可从档案独立重算"性质的方案：（a）在 runner 侧于评估进程退出、GPU 释放后再派生并封存（回执封存时点后移，但仍在 phase 封存之前）；（b）rollout 期间用现有 `observe_transition` 钩子的同一 `_Episode` 逻辑在线累积，档案重算只作离线核验。两者都不需要新的持久格式。

即用于本策略事实的字节约 3.7 KB，静态说明约 4.2 KB。主计划把"按 stratum 的画像与成功/失败对照"列为默认工作集，但当前裁剪顺序先删对照行、再删第三条时间线、最后才裁事件，结果对照表整段消失、时间线只剩尾部 5 个事件。可行的收紧方向（不增加预算）：把 `semantics` 里逐 phase 不变的规则/阈值/可操作性放入 prompt 级共享定义（现有 `diagnostic_table_definitions` 已是这种做法），作者投影去掉仅供机器比较的哈希（封存视图保留），去掉零行时的对照表头；释放的约 3 KB 足够放 20 行以上对照或第三条时间线。选例规则按 (stratum, cell, run, steps) 排序，取到的是字典序第一个 cell 里最短的失败，不一定是主导失败类型；这次取到的是 timeout 而 forbidden_contact 占该策略失败的 113/175。

Push 12 KiB 视图（11,718 B）没有这个问题：15 行画像 3.3 KB、两条时间线 4.2 KB，只裁 `final_pose`。

## 4. 生产接线与复杂度

- **源头 vs 补丁。** 行为派生只在两任务 `behavior.py`；封存在 `build_*_phase_summary`；公开投影/adapter/prompt 各一处消费。没有旧原型 import，公用层未获得任务语义。r6（401/402/403 服务拒绝后按全额预留继续）与 r7（输出超请求量按实计费、保留输入与总额硬限）都是最小改动，各有真实事件与定向测试。
- **重复的 required 映射。** `_Episode.observe` 把每个词条的 streak 长度作为参数传给 `_condition`，而终局关闭 open 区间时又用一段内联条件表达式重算同一映射；两处不一致时 `confirmed` 会在终局事件上出错。把 required 随 open 区间一起存即可消除。本次 864 回合一致说明当前两处相同。
- **4 处剥离 `behavior`。** `exploration.py` 两处、`prompt_adapter.py` 两处在把 summary 交给 `build_unified_stair_prompt_feedback` 前都做 `{k: v for ... if k != "behavior"}`，因为该函数严格校验键集合。在函数内允许/忽略该键是单点改法。
- **`project_stair_behavior` 的校验块**约 45 行逐字段核对自己生成的视图；`assert_public_projection_safe`、字节上限、分母守恒是必要的，其余键集合枚举偏重但无害。
- **Stair 侧 7 处函数内 `from ...behavior import`**（避免循环导入）与 Push 顶层导入不一致，无功能影响。
- **`compare_push_behavior`** 只在 all 组做计数差分，没有 Stair 那样的分层率差；目前没有真实 Push 父子对，可等有对时再改。
