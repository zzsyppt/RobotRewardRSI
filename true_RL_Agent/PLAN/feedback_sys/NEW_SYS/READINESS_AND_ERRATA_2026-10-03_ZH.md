## 1. 结论

可以动工，不需要再改一版计划。P0（冻结首批描述量）和 P1（现有 Stair 档案上的数值卡片加本地投递检查）现在就能做，不需要 GPU，也不需要调用模型。

第 3 节列了四件要在 P0 里定下来的事。它们不是计划的缺陷，是计划留给实施的决定；不先定会在 P1 中途返工。

## 2. 对我上一份审计的勘误

计划第 3.3 节指出审计里的说法有九处超出了脚本实际算的东西：表里八处，加上接触力口径一处。我逐条回到脚本和源码核对，九处都成立。

| 审计里的说法 | 实际情况 | 应当怎么说 |
|---|---|---|
| “足端的全部接触都已计入” | 错。[runtime_projection.py:48](../../../src/true_rl_agent/tasks/stair_climbing/runtime_projection.py) 写明档案里是法向接触力的合力，不含摩擦力。粗糙面和台阶棱上法向不竖直，竖直支撑有一部分走摩擦，档案里没有 | 足端法向力的竖直分量对不上体重基准；差额可能来自未记录的切向力、其它部位或质量基准，现有数据分不开 |
| 左后足“竖直冲量 15%，上台阶时” | 脚本用的是力的模，统计范围是全部成功回合的全部采样，不是竖直分量，也不只是台阶段 | 左后足法向接触力模的时间平均占四足合计的 15.3%。换成竖直分量是 15.1%，力模只算台阶段是 14.7%，数量级不变，但名称要对 |
| “同步率高，所以是齐跳” | 同步率是两只脚接触标记相等的比例，两只脚都不触发也算相等 | 状态一致率、落地时刻差、周期相位分别报告；不给步态起标准名字 |
| “每次腾空 0.14 秒” | 是单只脚一段完整不触发区间的中位数，不是整机离地 | 单足未触发区间中位 0.14 秒；四足同时未触发占 9.5% 另列 |
| “脚搁在地面上”“拖腿” | 量到的是足端参考点离投影台阶面的竖向差、速度和水平位置 | 参考点离参考面约 2 cm、速度接近 0、接触标记未触发；不断言脚底贴地或拖地 |
| “其余由别的部位承担，最可能是小腿” | 见第一行；另外 150.9 N 是一个成功子集的代理基准，不是每个环境的真实重量 | 只作为待查线索 |
| “每一步都有归属，全程覆盖做到了” | 脚本把短于 0.3 秒的段并进前一段；r1.e129 以躯干接触终止，时间线上却只剩“迈步前进” | 平滑不能删短事件；时间分配率不等于必要事实召回 |
| “这一项在几乎每次落地时都是负的” | 用控制步的接触标记重建的腾空时长；真实奖励用传感器自己的计时、首次接触和命令门控 | 代理时长达到 0.5 秒的占 0.8%；真实分项要补采后才能说 |
| “整回合误报压到 5%” | 两种统计量分别是 4.4% 和 7.5% | 按具体统计量报告 |

计划第 16.1 节没有采纳的几条，我同意它的处理：干预标签不等于实际出现的行为；统计单位由要声明的问题决定；视觉有没有增益要实测；拟合浅决策树算拟合模型。

这些勘误不改变审计的主要建议。它们恰好说明计划第 6.5 节“每个描述量带允许措辞和禁止推断”这一条是必要的：我自己写的探针就犯了命名强于测量的错。

## 3. 要在 P0 里定下来的四件事

### 3.1 新卡片从哪里进作者请求

现在只有一个接缝，三处写死了版本：

- [phased_evaluation.py:186](../../../src/true_rl_agent/tasks/stair_climbing/phased_evaluation.py) 调 `build_stair_process_behavior`，结果放进 `evidence["behavior"]`。
- [behavior.py:528](../../../src/true_rl_agent/tasks/stair_climbing/behavior.py) 的 `project_stair_behavior` 按 `schema_version` 字符串分发。
- [prompt_adapter.py:3294](../../../src/true_rl_agent/tasks/stair_climbing/prompt_adapter.py) 只对 `public.v4` 附加父代差异。
- [process_report.py:558](../../../src/true_rl_agent/tasks/stair_climbing/process_report.py) 的校验要求 `comparison_summary` 每个分层恰好含旧的四个模式词，并且 `lexicon_version` 固定为 `stair.process_terms.v1`。

共享契约 [evaluation/process_report.py](../../../src/true_rl_agent/evaluation/process_report.py) 只管句子的形状和容量，不限制措辞，所以卡片的句子可以直接放进现有七个区。但信封字段是旧词表的。沿用旧版本号装新内容会让版本说谎，父代比较也会把新旧报告当成同一种。

所以 P1 的“本地投递检查”实际包含一次任务报告的版本升级：新的公共版本号、新的词表版本、`comparison_summary` 的键跟着目录走、上面三处分发各加一个分支，旧版本保留可回放。建议把它写进 P1 的工作项。

### 3.2 P1 的范围

计划第 5.1 节的证据协议和第 6.2 节的表达式树都是通用设计。P1 只需要启用的描述量用得到的那部分：描述量写成有类型的函数加契约条目，模板直接引用。给模型填参数的开放查询入口等 P2 用到再做。

首批描述量建议不超过十个，够填满卡片的四块即可：进度与停滞区间、机身姿态与翻转方向、每足接触标记占比、单足未触发区间、接触组合、落地时刻差与相位、法向力模占比、关节到名义限位的距离、足端参考点相对躯干的位置、躯干间隙的近似量，加上任务层的台阶位置和终止余量。

### 3.3 作者读到的措辞

第 9.3 节的示范句是准确的，但“接触阈值标记占比”这类词对作者模型不透明。之前的真实调用里，作者把“rule-negative”猜成了别的意思。两种办法里选一种：每句都带限定，或者在固定说明里把术语定义一次、句子里用短词。后者省字节，8192 字节的容量也更够用。同时定下作者侧用英文还是中文；现有报告是英文。

### 3.4 工作区和开发环路

- 工作区现在有 37 个已修改的跟踪文件和 44 个未跟踪项，全是之前阶段留下的。开工前提交或打快照，新包才有干净的对比基线，服务器也才能同步。这需要你决定，我不会自行提交。
- 档案在服务器上，解码一遍约 3 分钟 CPU。P1 的代码要么在服务器上跑，要么先把逐步数据导出到本地。

## 4. E1 的必要事实清单（R4 Stair，初稿）

计划第 13.2 节要求在看系统输出之前先定清单。下面是由两次审计得到的队列层事实，措辞已按第 2 节改过。数字来自探针，属于开发材料；新系统独立算出来对不上时，两边都要查。

1. 864 回合，成功 682；终止原因：躯干接触 125，超时 39，姿态失稳 16，打滑 1，偏离路线 1。
2. 成功回合在台阶段的每足接触标记占比：左前 0.72、右前 0.73、左后 0.38、右后 0.61；682 个成功回合里左后都是最低的。
3. 接触组合：左前、右前、右后触发而左后未触发占 39.7%；四足都未触发占 9.5%。
4. 相对左前足的落地相位：右前 0.97、右后 0.08、左后 0.79；落地间隔约 0.5 秒。
5. 单足未触发区间中位 0.14 秒，达到 0.5 秒的占 0.8%。
6. 左后小腿关节在名义伸直限位 0.02 rad 以内的时间：台阶段 74%，平地 28%。
7. 左后足参考点平均在躯干原点后方 0.40 m，默认站姿是 0.18 m。
8. 行进中出现躯干接触的失败 78 个：终止前半秒前进速度中位 0.47 m/s；躯干间隙近似量中位 2 cm；成功回合里 22% 曾低于 2.5 cm；`height_ood` 层 50 个失败里占 34 个。
9. 先停滞后翻转的失败 56 个：向右 35、向左 14、向后 7。
10. 超时 39 个：26 个前足在第 1 级、后足在地面（15 个有一只后足接触标记持续未触发，8 个四足都触发且无迈步，3 个有迈步无进度）；7 个在粗糙面分层的台阶中途；1 个一只前足未触发；5 个最后 3 秒仍有进度。
11. 直立且躯干未受力时，单足接触标记连续未触发 2 秒以上：超时 18/39，成功 0/682，其它失败 0/143。
12. 最后 3 秒有一只后小腿关节超过 90% 的时间在名义伸直限位附近：超时 34/39。
13. 足端法向力竖直分量的时间平均：常规台阶成功回合约 151 N，粗糙面分层约 108 N。标为未解决的残差。
14. 缺口：没有逐步动作、力矩、奖励分项；非足端连杆只有躯干有接触力；没有每个环境的实际质量和有效限位；没有父代档案。
