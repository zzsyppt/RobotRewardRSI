# 第四次审计：Phase 0 基线是否为后续阶段打好了基础

日期：2026-09-23。对象：`PLAN/feedback_sys/P0/` 全部产物与总计划 v1.2.2 的 Phase 0 条款。方法：重跑 P0 自己的校验器和三套回归；用独立脚本重算关键数字；读 P0 手头已有但未分析的原始数据；在服务器做一次真实重放试验。所有新计算在 [p0_audit_checks.py](../p0_audit_checks.py)，输出在同名 JSON。本审计没有改动 `P0/` 封存目录中的任何文件。

## 0. 结论

P0 作为"证据、成本、身份、资源的基线"是可信的，重跑全部通过。但 P0 对"后续 phase 需要什么"给出了三个偏保守的答案，其中第一个会直接改变 Phase 2/3 的做法：

1. **可比 candidate 不是缺失，是没有去找。** formal c6 的 23 个 `best.pt` 与当前 Go2 v3 reference 的策略 IO、观测、动作、agent 配置、训练 profile、训练 binding、训练 cell manifest 全部同 hash；v3 reference 本身就是一条在 v2 cell 训练、在 v3 套卷评估的策略。现有 P6 重放脚本对 formal Gen8-A 预检通过，真实重放也已完成：Gen8-A 在 v3 public-dev 得到 822/864 成功、J_primary 0.9244，reference 为 689/864、0.7467；两条策略的禁触前置事件截然不同（§3）。这意味着 22 条不同策略、15 对真实 parent→candidate、36 条真实作者 rationale 都能以约 2 GPUh 的代价放进当前协议。Push 同理：attempt_08 有 10 个 force v3 候选、2 个 accepted，逐回合 facts 已在本地，checkpoint 在服务器，P0 没有入库。
2. **已有数据能回答的问题比 P0 写的多。** 失败发生在哪一层、哪个 cell、已有诊断标志有没有区分力，这些都能从 P0 手里的 864 条 facts 直接算出，而且是 Phase 2 锚点设计和 Phase 3 词表的直接输入。P0 只算了 primary×flag 的共现表，没有往下走一步。
3. **作者今天怎么用证据没有记录。** attempt_08 的 10 条 rationale 表明作者已经在引用分数、失败计数、分层、sibling 负证据，并推导奖励核的斜率；它唯一没有的是过程证据。这个"A 臂基线"决定 T 必须提供什么、盲评应该看什么，P0 手里有 53+10 份材料却没有看。

过度复杂化确实存在，集中在封存仪式、strict-token 资格、四层资源矩阵和防御性文风四处，见 §4；这些不影响基线可信度，但会被后续 phase 复制，所以要现在停。

### 2.2 Go2 v3 的失败结构，Phase 2 锚点与 Phase 3 词表的直接输入

从 P0 已有的 864 条 facts 重算（[p0_audit_checks.json](../p0_audit_checks.json) `go2_v3_public_dev`）：

- 禁触发生在攀爬中段，不在起步。禁触回合的 `progress_fraction` 十分位分布为 2:18、3:12、4:8、5:22、6:27、7:17、8:8、9:1，中位 0.60；闭合步 90–633，中位 291。成功回合闭合步中位 322。所以"按同一级立面对齐"不是可选项，是必需项，而且要对齐的层级横跨 2–9 层。
- 失败高度集中在少数 cell。`c1_conditional_frontier_level_5` 36 回合里 30 禁触、2 成功；`height_ood_level_5` 19 禁触、9 成功；`height_ood_level_4` 16 禁触、19 成功；`joint_ood_level_3` 12 禁触、16 成功。另有 10 个 cell 36/36 全成功。这意味着计划里的 `no_comparable_success_control` 分支不是边角情况，而是最重要的失败 cell 的常态；Phase 2 的对照组必须允许跨 cell 的同层级成功样本，否则最有价值的失败没有对照。
- 已有诊断标志只有一个有区分力。成功组与禁触组的标志率：`base_orientation_instability_detected` 1.6% 对 41.6%；`slip_detected` 81.3% 对 91.2%；`insufficient_clearance_detected` 7.3% 对 7.1%。slip 在 83% 的回合里都出现，clearance 在两组里同率；两者按现定义几乎不携带信息。P0 §5 的表只列了 slip 和 clearance，漏掉了唯一有区分力的 orientation。对 Phase 3 的含义：旧 slip/clearance 规则不能原样进入 T 词表，必须用时序重定义；对 reference 这条策略，"禁触前有哪些可测事件"的第一个候选答案是姿态失稳，而不是滑移。§3 会说明这个答案是策略特异的。

### 2.3 作者当前如何使用证据（A 臂基线）

attempt_08 的 10 条 rationale（本地 `provider_candidates/*/components.py`）全部：引用 parent 的 public-dev 均分（如 0.8802、0.9115）、失败计数（如 15 fall_side 对 1 fall_forward）、分层成功数（37/48 high）、sibling 的负证据与其分数；然后推导奖励核在某个状态区域的斜率并解释为何要改。formal c6 的样本同样引用 objective 与 joint_ood 成功率。

作者从不拥有、也无法引用的是过程事实：倒下从哪一步开始、先失守的是哪个条件、腿在做什么。像"the base dropping and rotating faster than the legs can replace support"这样的机制说法是猜测。这就是 T 必须增加的层，也是盲评应该核对的层：T 若只是把计数换个格式，A/T 不会有差别。P0 没有记录这个基线，Phase 3 启动卡应该补上。

### 2.4 Phase 2-min 的量级

- recorder 每步每 env 采集：joint_pos 12、base pos 3、base quat 4、support pos/vel/force 各 4×3、forbidden force 1×3、episode_length 1、两个 term mask 与 done。约 100 个标量，float32 约 0.4 KB。288 env × ≤640 步 ≈ 70 MB/seed，一次 public-dev 三 seed ≈ 0.2 GB；22 条策略 ≈ 5 GB，在 P0 登记的 6 GiB Phase 2 额度边缘，用 float16 或只存 forbidden 力范数即可减半。
- 重放成本：P3 资格评估 public-dev 分段 422 s；P6 同 checkpoint 回归分段 288 s，进程总墙钟 310 s。按 6 分钟/策略计，22 条策略约 2.2 GPUh，远低于早期路径 36 GPUh。P0 的 Phase 2-min 上限"6 次 runner 启动"容不下这件事，需要改为约 30 次。
- 碰撞部位的可观测边界：binding v3 把 `forbidden_contact` 角色收窄为 `["base"]`，robot profile 中的 15 个禁触刚体（头、髋、大腿、小腿）不在终止条件里，也不在 recorder 里。所以"哪个部位撞到立面"现在只能回答 base；大腿或小腿撞击既不终止也不被记录。contact sensor 已经覆盖全身（`prim_path` 为 `Robot/.*`），把 15 个刚体的力范数加进 recorder是零新传感器的改动，应作为 Phase 2 的可选 profile 登记，而不是在计划里继续写"不能判断碰撞面"。

### 2.5 token 估算

9 个实测点（4 个校准 + 5 个验证）的 tokens/byte 在 0.260–0.330 之间。线性拟合 `tokens ≈ 0.363×bytes − 5252` 的最大误差 5.7%；P0 冻结的 `0.4123×bytes + 512` 高估 27%–62%。对于 1M 上下文、3 万 token 级的输入，严格上界没有工程意义；对于费用对账，高估一半的估算也没有意义。建议改成线性拟合加 usage 对账。

三点直接影响计划：

1. **禁触的前置事件是策略特异的。** reference 的禁触有 42% 先出现姿态失稳，Gen8-A 只有 6%，却有 18% 出现低净空。同一个"禁触前发生了什么"的问题，在两条策略上答案不同。只用一条 reference 做首个最小闭环，得到的画像会被当成任务的普遍规律，而它只是那条策略的习惯。
2. **旧 slip 标志是 reference 的步态特征，不是任务特征。** 成功组 slip 率从 81% 降到 27%，说明这个标志有信息，但信息在"策略之间"，不在"同一策略的成功与失败之间"。这正是 BehaviorDiff 该承担的层，也说明 P0 把 Diff 定为 missing 会让 Phase 3 失去最有区分力的视图。

## 4. 过度复杂化：哪些该保留，哪些不该被后续阶段复制

保留（直接服务后续 phase，成本低）：源码/协议/binding 的 hash 绑定；五类输入的真实 usage 回执与缓存观察；单帧图像传输探针；远端 checkpoint 存在性核查；两份字段级"已采/已存/已投影"地图；真实回归而不是读旧日志。

不该复制或应删减：

1. **封存与负向对照仪式。** `p0_seal.json`、`hash_mismatch_negative_control`、`missing_extra_receipt_negative_control`、"不追认成调用前已经程序化强制冻结"这类语义，对单人研究项目的价值接近零，却给每个后续 phase 立了模板。后续 phase 只需要一份文件 hash 清单和现有单测。
2. **strict-token 资格。** P0 自己写明模型有 1M 上下文，而输入最大 3 万 token；"严格 token 上界 INCONCLUSIVE"是一个不需要回答的问题。建议从计划的验收项中删除，保留线性估算与 usage 对账。
3. **资源矩阵。** `resource_limits.json` 是 4 个层级 × 5–8 个维度，加上"墙钟不是经过时间"之类的解释。项目真正需要的是两个数（GPUh、美元）和每阶段一行的分配；其余维度在 journal 里已有回执。
4. **3,200 条"内容去重病例"。** 9.9 MB 的 JSONL 只覆盖 2 条 Stair 策略和 6 条 Push 策略，全部信息已在原 summary.json；"去重数不是独立样本数"的反复声明说明作者自己也知道它不是案例集。真正的案例集是 §2.1 的两条谱系。
5. **文风。** 8 份文档 6.9 万字里有 404 个"不能/不得/不冒充/不等于/不代表"类限定，平均每句 0.4 个，Stair 地图达到每句 0.6 个。读者要花一半时间跳过免责声明才能找到事实。建议每份文档只留一段"边界"，正文陈述事实。
6. **计划层面的两名独立盲评者。** 这是单人项目做不到的要求。可改为：引用正确性由机械核对（transcript 是机器可读的，引用是否存在、数值是否一致可以程序判定），判断质量由一名人工评审。

以上六项里，1–4 是 P0 自己加的，5–6 来自计划文本对 P0 的要求；用户在 Phase 0 验收条款里要求"hash、attempt、seed、祖先"核对是合理的，但 P0 把"核对"做成了"封存系统"。

## 5. 建议对计划做的小侵入修改

1. **Phase 2-min 案例集。** 首个 profile 仍是 Go2 Stair v3，但案例集改为"当前 reference + formal c6 的 22 个不同 best.pt 在 v3 public-dev 上的重放"，用现有 `stair_dev_regression.py` 加时序 recorder 一次完成。BehaviorDiff 从 `missing_comparable_candidate` 变为可得；预算从 6 次启动改为 ≤30 次、8 GPUh 不变。重放得到的分数是新评估域下的分数，只用于行为反馈开发，不与历史 v2 分数比较，不宣称历史增益。
2. **Phase 3-min 案例来源。** 12–24 个案例取自 formal 15 代与 attempt_08 5 代的 parent→candidate 对；A 臂输入就是当时真实发送的 payload（53 份与 15 份都在），T 臂在同一 payload 上替换为画像与差分。这样 A 臂不需要重新生成，盲评的"事实核对"有真实结局可以对照。
3. **Phase 5 裁决 fixture。** 用 formal 36 条 rationale 中的机制主张与它们的真实 public-dev 结局，做裁决规则的离线测试集；这是事后数据，只做规则测试，不算预测命中率。
4. **Phase 3 启动卡增加 A 臂基线一段。** 记录作者当前引用了哪些字段、做了哪些无法核实的机制推断；T 的增量只以"新增了作者过去无法引用的过程事实"计。
5. **Phase 2 增加可选 profile：15 个禁触刚体的接触力范数。** 因为计划明示要回答"碰撞位置"。
6. **删除 strict-token 验收项；两名盲评者改为一名人工加机械引用核对。**
7. **Phase 2 对照组定义。** 明确允许"同层级、跨 cell 的成功回合"作为对照，并单独报告 `no_comparable_success_control` 的 cell 数；否则 `c1_conditional_frontier_level_5` 这类 cell 没有对照。
