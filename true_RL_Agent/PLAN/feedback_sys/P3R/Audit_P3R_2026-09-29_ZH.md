# P3 / P3-R 进程审计（2026-09-29）

审计者：Claude（Fable 5.1），独立于 P3 评阅流水线与 R.0-b 评阅者。范围：P3 记录与模型评阅是否准确、公正；P3-R 已登记的 R.0-a / R.0-b / 无条件工程修正是否与服务器回执一致；下一步。方法：只读复算（不改原评分、原结果、生产代码），服务器哈希核对，隔离目录重跑复算脚本，以及对 R.0-b 的 8 项独立盲评复核。复核材料在 [audit_20260929/](audit_20260929/)。

## 1. 结论

1. **P3 记录准确、可复现。** 冻结哈希、53 份材料对应的服务器结果文件哈希、门指标全部从评分表独立重算一致；账本 92 槽 / 89 已知回执 / US$2.772 与服务器 usage.json 一致。
2. **P3 模型评阅的方向可信，幅度与归因有限。** 按案例配对，12 个案例中 11 个 T 的事实支持率低于 A、10 个关键硬错更多（符号翻转置换检验 p≈0.002）；逐项聚类自助 95% 区间 T−A 事实支持率 (−0.139, −0.033)，关键硬错/项 (+0.46, +1.54)。行动相关性差异区间含 0。盲化只是名义上的（T 有 18/24 项可由输入看出条件），且 T 的劣势集中在行为块可见的项（可见 0.824 vs 不可见 0.892 vs A 0.927；T 不可见组与 A 的差异区间 (−0.089, +0.038) 含 0）。这些与 v1.1 计划已登记的混杂一致：不能把 P3 读成“过程反馈有害”，只能读成“这一版投递没有帮上忙”。
3. **P3-R 已登记的进程与服务器一致，工程可逐字节复现。** R.0-a 两轮 16 次请求、R.0-b 34 次请求的回执均为 high / thinking 开启 / 上限与登记相同；封存卡、冻结规则、四份评阅文件、汇总文件的哈希与引用一致；Stair v2 完整派生和 v3 视图、Push v2 三个输出在隔离副本里从原始 NPZ 重算后哈希与交付件完全相同；62 个单元测试通过。
4. **R.0-b 的“Tc-num 有效”判定经不起第二位评阅者。** 该判定只依赖 2 项（001、018）。独立盲评复核 8 项：018 完全一致；001 被判行动相关性 1、硬错 1（代码 keep 系数在驻留判定带内降到 0.625，与“直立段保持完全阻尼”的叙述矛盾，已由本审计从源码直接核实）；022（Tc-vis）被判行动相关性 1。若以复核分替换，Tc-num 只剩 1 个案例，不满足“至少两个不同案例”；Tc-vis 仍满足（push-04、stair-01）。按事前判定表应落到“仅 Tc-vis 有效”一行，而不是“Tc-num 有效”一行。**原评分不改，但该门的状态应登记为“有争议、待裁决”。**
5. **模型评阅公正性的结论：** 数字与代码事实核对在两位评阅者之间稳健（所有引用数字均被双方定位并核实）；两项决定过门的定性判断（行动相关性是否为 2、硬错是否为 0）评阅者间一致率分别为 5/8 和 4/8，分歧方向双向（对 A/T0 和对 Tc 都有更严与更宽的情况），未见系统性偏向某一臂。因此单评阅者的模型评阅可用于定位问题，不足以单独裁决只差 1–2 项的门。

一致率：行动相关性 5/8，机制 6/8，硬错是否为 0 4/8，是否达标 6/8；原判达标的 3 项只有 1 项在复核中保留。

关于 001 的硬错，本审计从 `proposal-001.py` 直接核实：`keep = 1 − 0.75·clamp(tilt/0.4, 0, 1)` 无死区，tilt = 0.1 / 0.2 / 0.283 rad 时 keep = 0.8125 / 0.625 / 0.470，而 rationale 写明“the upright regime keeps full dwell-aligned damping because that is the regime the task judges for dwell”（驻留判定带为 |roll|,|pitch| ≤ 0.2 rad）。这是口径内的“代码与描述矛盾”。

反事实：仅用复核分替换这 8 项、其余 24 项保持原分，各变体达标的不同案例为 A 0、T0 0、Tc-num 1（push-02）、Tc-vis 2（push-04、stair-01）。按事前判定表为“仅 Tc-vis 有效”。

其他观察：
- 8 位复核者均能从输入格式判断条件（其中 1 位把 Push 的 T0 误认为 Tc-num），印证“盲化有限”；未见按条件打分的迹象。
- 分歧集中在两类：硬错的口径（分母/范围措辞、合成反例是否算矛盾）与“行动相关性 2”对“过程预测”的要求。这两类恰是过门条件。
- R.0-b 评阅者为 Codex 模型代理（四份文件身份写法不一，stair-01 文件缺 reviewer 块），P3 评阅者为 Claude；两轮都不是人类评阅，文档已如实登记。
- 人工整理的纯数值输入反而提高作者硬错率：每项硬错 A 0.62、T0 1.12、Tc-num 2.00（Stair 3.25）、Tc-vis 0.62。Stair Tc-num 4 项无一达标。现有作者对密集数值过程证据的误读不因人工整理而消失；Tc-vis 只多了几句由录像核对的短叙述，硬错回到 A 的水平。

## 5. 问题清单（按严重度）

1. **判定层：** “Tc-num 有效 / 数值开发门通过”依赖 001 的 AR 2 与硬错 0，独立复核不支持；应登记为有争议并裁决后再引用。
2. **流程层：** 解盲前的定向复核（009、027）由掌握调度/映射的根代理指定项目发起；本次未改变任何变体的达标案例数，但该渠道在 R.4 必须关闭（复核只能按错误类别全体进行，由无映射权限方发起并先登记）。单评阅者裁决只差 1–2 项的门不够；R.0-a 通过是两轮中取通过的一轮（合并 14/16=87.5%），文档已披露，R.4 靠 5 次尝试与保留证据的修复帧缓冲。
3. **设计风险：** Stair 纯数值 0/4 且硬错 3.25/项；R.4 要求两任务分别过门，按现状 Stair 半边大概率不过。新 v3 视图已把翻滚方向（up_z<0）、回退、带符号姿态写成数值，但尚未在作者身上试过。
4. **记录卫生：** 四份 review_completed.json 的 reviewer 字段结构不一，stair-01 缺失；建议统一登记评阅者身份与后端版本“未提供”。
5. **环境：** 采集前须再核 GPU（本次审计期间曾被他人 vLLM 占满，用户已释放）。
6. **版本管理：** P3 以来的源码、测试、P3/P3R 材料均未提交；建议先提交再启动采集。
