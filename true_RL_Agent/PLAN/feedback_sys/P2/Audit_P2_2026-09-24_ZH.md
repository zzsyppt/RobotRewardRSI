# Phase 2 独立审计（2026-09-24）

审计对象：工作树中未提交的完整 Phase 2（起点 `b24ddfe9`），以 [P2 验收](./ACCEPTANCE_ZH.md)、[实施卡](./IMPLEMENTATION_PLAN_ZH.md)、[字段目录](./FIELD_CATALOG_ZH.md) 及主计划 v1.2.6 的 Phase 2 严格验收为对照。审计方式与 P1 相同：不读开发记录当结论，在服务器上对真实档案做只读重算与探针，本地跑全量测试与反例。所有新脚本、服务器输出与 hash 在 [audit_probe/](./audit_probe/)（`summary.json` 汇总）。审计过程 0 次 GPU、训练、模拟器与模型调用，未改动任何档案或回执。

## 1. 结论

**声明范围已实现，没有单源真相或语义一致性方面的大问题；可以在处理下面第 5 节的两个信息缺口后开 Phase 3。** 具体：

- 15 份真实档案（Stair 3 × 864 回合，Push 12 × 64 回合）用**当前工作树源码**在服务器上独立重算，全部与封存回执相等（`recompute_current.json`）。这证明 r2 采集的档案与最终提交的源码互相可读，不只是与冻结快照互读。
- 档案与 phase 回执的绑定是单向、封存前完成的：生产者在封存前核 identity 与 summary 相等；回放只结构校验引用，不要求原路径在线（`canonical_stair_phase_result_summary`、`test_numeric_archive_is_bound_to_exact_phase_and_summary`）。这一点在 r1→r2 的 `phased_evaluation.py` 差分里能看到是主动修正的。
- 采集异常不会被算到候选头上：Stair 边界只转换 `StairRewardProgramError`，`NumericEvidenceError`/`ValueError` 原样穿出；Push 适配器同样原样穿出，训练脚本的通用 `errors` 路径在 runner 里判为基础设施失败而非候选失败。两条路径都用反例实测（`summary.json:capture_failure_attribution`）。
- 共享层确实很薄：`numeric_evidence.py` 147 行、`training_numeric_capture.py` 152 行，不解释任务；任务语义、坐标、终局、复算都在任务模块。
- 真实资源：0.83 GPU 容量小时，采集 rollout 开销 ≤ 2.2%，配对 RSS 差 ≤ 22.7 MB，与验收表一致。

需要报告的问题集中在“信息是否足量”而不是“是否正确”：Stair 档案存的禁触身体接触力是瞬时值，而终止判据看的是 3 帧历史最大值，parent 的 72 个禁触回合里 26 个（36%）整段档案中禁触身体力向量全为 0；训练采样 3 个窗口各 8 个连续步在同一 rollout 内，相邻步自相关最高 0.98，对“训练早/中/晚各项贡献如何变化”几乎没有分辨力。两者都是小改动，但应在 P3 定义词表之前定，否则 P3 会在缺操作数的字段上建描述。

## 4. 单源真相与语义一致

- **一条绑定链，方向正确。** 训练/评估进程写档案 → `complete()` 原子发布 manifest → 引用（路径 + manifest SHA）进 `task_evidence`/`training.numeric_evidence` → 进已有 phase/训练回执 hash。Stair 生产者在封存前把档案 identity 与回执 identity、`metadata.summary` 与 `task_evidence.summary` 逐项比对；Push 生产者比对 `runtime_episode_records == per_episode`。回放侧只校验引用结构。没有第二份真值：档案里的 `summary`/`per_episode` 是回执内容的副本，用于自证，不参与决策。
- **`complete` 三义分离清楚。** 归档 complete ≠ 回合完整（`episode_coverage`、`valid`）≠ 训练成功（`training_status`）≠ 媒体存在。字段目录、投影 allowlist 与测试三处口径一致。
- **状态词表没有膨胀。** 训练窗口 5 个状态、整体 4 个状态、Push 恢复覆盖 7 个状态，都是从实际分支得来的，没有泛化事件词表。
- **提示词与记忆不复制时序。** 经 `PublicContextBuilder` 检查，generation 路径的作者输入只多出 `runtime_feedback_summary.latest_runtime_activation.training_sampling`（1.1 KB，仅覆盖簿记）；14 KiB 记忆只存 lane 短状态，与 P1 门槛一致。
- **来源准入没有放宽 hash。** Stair 从 registry 重编译每个祖先节点并核完整训练绑定；Push 重编译两端 manifest、重建 TrainingBinding 与原回执比对，并要求 argv 不重标 subject/checksum。两者都只允许 eval。
- **一处记录不一致。** 总账里 `r2_parent_on`、`r2_gen8_on` 的角色是 `acceptance_attempt`，但 `launch_receipt` 为“未记录的手工运行”。它们的来源靠档案 identity 键与 on/off 共同的 source preflight hash 可以判定（见第 2 节），但 `run_inventory.json` 与验收报告都没有写出这个判定依据。建议补一句来源判定，不要重跑。

## 5. 信息是否足量、是否爆炸

### 5.1 Stair：禁触身体的力操作数缺失

`isaaclab_runtime_env.py::record_post_step` 存的是 `contact_data.net_forces_w`（瞬时净力）。而 `base_contact` 终止项与 reward 输入的支撑接触判断都用 `net_forces_w_history`（`contact_history_length=3`，取 3 帧最大范数）。控制步 0.02 s 内 decimation 多个物理子步，接触常在子步内发生并在步末消失。实测三份档案：

| 策略 | 禁触回合 | 终止帧禁触力非零 | 整段回合任意帧非零 |
|---|---:|---:|---:|
| parent fca6a59c | 72 | 46 | 46 |
| Gen8-A bcd8de3a | 34 | 24 | 24 |
| G1 reference | 197 | 186 | 186 |

即 Go2 约 30–36% 的禁触回合，档案里找不到任何一帧禁触身体受力，只能知道 manager 项在终止帧为真。首问题“禁触前出现了哪些可测事件”里的“受力大小/方向”因此对这部分回合不可回答；P3 若基于力向量做“撞击方向”描述会系统性漏掉这些回合。支撑脚也一样：archived `support_contact_forces_w` 是瞬时值，decoder 的 `support_contacts` 用瞬时值阈值判定，与 reward 侧的历史最大判定不是同一操作数（这不影响终局重算相等，因为终局判据本来就用 decoder 视图）。

建议（P3 前、小改）：在 recorder 里额外保存禁触与支撑身体的 3 帧历史力向量，或至少保存每身体的历史最大范数。后者 Go2 每步 5 个 float32 × 288 env ≈ 5.8 KB，整档（1,632 个向量步）约 +9 MB 原始，压缩后更少；前者约 +85 MB 原始但多为零。这是新字段、新 profile 版本，不回填旧档案。

### 5.2 Push：每步姿态只有范数，方向丢失

`pose[...,6]` 存高度、有符号 roll/pitch、平面速度范数、角速度范数、漂移范数。每回合的推力方向是有的（v2 `requested_delta_v_world_mps` 2 维，v3 `force_world_n` 3 维，均在 `runtime_episode_records`），但每步的 `root_lin_vel_w.xy` 和 `root_pos_w.xy − reset.xy` 只剩范数，无法判断“顺推方向倒/逆方向退/侧向滑”。这与 P3 最自然的 Push 词条（“被推后向推力方向倾倒/迈步”）直接相关。把两个范数换成各自的 2 维向量只增加 2 个 float32/env/步（每 seed 档案约 +0.2 MB），范数可离线求得。同样是 profile v1 → v2 的小改，现在改比 P3 之后改便宜。

### 5.3 训练采样：数量小但信息更小

固定 3 窗 × 8 连续步 × 16 env。对 48000 步的正式训练，三窗分别是第 1–8、23997–24004、47993–48000 步，每窗只覆盖 0.16 s 的机器人时间，且早窗是 reset 后前 8 步（站在出生点）。r5 Push Go2 档案的相邻步自相关（`upright_height` 0.62–0.98、`joint_pose` 0.60–0.94）说明每窗有效样本远少于 8。它能证明接线、时钟与 raw×weight→total 的算术，这一点 4 组真实配对已验证；但它回答不了“某项贡献在训练中如何变化、何时开始非零”。

现有 `StairCompleteRewardDispatcher._record_evidence` 已经每 `evidence_interval_steps` 计算每项 mean/nonzero/max_abs，只是不保留历史（只留 last）。把这些按间隔的聚合追加进同一个数值档案（每间隔每项 3–4 个标量；2000 迭代 × 8 项 × 4 × 4 B ≈ 256 KB）比现在的 24 步原始样本更有用，也更小于任何上限。Push 适配器可做同样的事。建议在 P3 需要“训练阶段摘要”前替换或补充，不必现在重跑。

### 5.4 体积与提示词

- 每次 Stair public-dev 采集 52–68 MB；每代 2 次 lane public-dev，父策略更替时再加 1 次 guard public-dev（`replay_generation_guard_chain` 复用未变父策略的 guard 回执），15 代上限约 2.5–3 GB；Push 每次 1.6–2.2 MB。都远低于 2 GiB/档案上限，磁盘可承受。
- 41% padding 帧已置零，压缩后代价小，不必改分块策略。`episode_length`、`control_step`、`terrain_types` 用 int64 可改 int32（parent 档案省 ~2 MB 原始），优先级低。
- 作者提示词只多 1.1 KB 覆盖簿记；其中 3 窗各 6 个整数对作者判断无用。若要减负可压成 `status + 三窗状态 + archive_manifest_sha256`（约 150 B）。width-one 旧路径的最近轮条目会从 312 B 涨到 1.5 KB，8 KiB 上限内会挤掉更早轮次；该路径已非正式主线，只需记录。

## 6. 复杂度与不必要的防御

规模：新增生产模块 1,085 行、脚本 848 行、既有文件 +521/−81；新测试 1,558 行、改动 +162/−5；PLAN 验收工具 1,806 行；P2 目录 16 MB（6.3 MB npz 副本 + 9.0 MB JSON）。相对于一个“保存足以重算行为的证据”的阶段，量级合理，没有引入数据库、后台服务、通用事件词表或迁移框架。以下是可以更薄的地方，按收益排序：

1. **Push reducer 复制了终局标签逻辑。** `recompute_push_numeric_evidence` 用 numpy 重写了 fall/invalid/success 分类与 dwell/恢复锁存（约 60 行与 `runtime.py`/`force_runtime.py` 平行）。今天 768 回合全等，但协议 v4 改判据时要改两处。Stair 走的是复用生产 decoder/tracker 的路，没有这个问题。建议把 Push 的逐步稳定/dwell/标签抽成一个 torch/numpy 无关的纯函数供运行时与 reducer 共用；中断、失败条件计数等新分析留在 reducer。
2. **Push 准入手工重建 TrainingBinding。** `validate_push_reference_evaluation_source` 逐字段构造 `TrainingBinding(...)`，与 `IsaacLabRslRlBackendAdapter._training_binding` 平行；绑定加字段时会漂移。建议共享一个构造函数。
3. **失败 lane 的采样桥接横跨 7 个文件**（`candidate_failure`、`subprocess_runner`、`round`、`generation_record`、`generation_contract`、两个 prompt adapter、`mechanism`），换来的是“候选训练失败时作者能看到采样窗口覆盖到哪一步”。签名上它没有改变 source/score 选择，`include_failed_training_sampling` 默认关；但 `project_generation_public_history_record` 为失败 lane 再次加载 `validate_generation_ledger_record` 已经加载并校验过的执行回执，是多余 I/O。价值低于成本，若 P3 不依赖它，可考虑收回或至少复用已加载对象。
4. **两套 Stair 回放入口并存。** P6 的 `stair_dev_regression.py`（PLAN）与 P2 的 `scripts/stair_numeric_dev_replay.py`；后者 `_completed_source` 80 行重复校验原训练回执，而 runner 的祖先准入 hook 在启动前还会再校一次。可接受，但应指定后者为唯一入口，避免两处漂移。
5. **验收脚本的 `behavior` 段是 P3 逻辑的原型**（事件计数、锚点、终局前 1 s 窗口）放在 PLAN。作为验收工具没问题；P3 实现时要在 `src` 重写为任务所有，不要 import PLAN。

没有发现为小概率事件堆砌的防御：`NumericEvidenceWriter` 的检查（命名数组、dtype 类别、块/档案预算、单次发布）每条都对应真实失败；`validate_numeric_evidence_reference` 的严格字段集是回放路径的必要条件。
