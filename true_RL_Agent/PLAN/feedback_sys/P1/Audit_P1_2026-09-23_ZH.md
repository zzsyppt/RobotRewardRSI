## 3. 发现的问题

### 3.1 逐 lane 测量列使真实会话的记忆保留减半（建议 P2 前修复）

`experiment_memory` 在每个 generation 条目上新增了两处测量：`trial_outcomes` 第 10 列（每 lane 一个 7 键字典，缺测键写 `null`）和顶层 `runtime_observation`（被选 lane 的同一字典再复制一次）。在 14 KiB 记忆预算下，真实 formal c6 会话的保留代数如下（保留代数 / 省略代数 / 记忆字节）：

| 构建点 | 基线 fe96455d | P1（完整字典） | 变体 sparse | 变体 sparse+去顶层 | 变体 token |
|---|---|---|---|---|---|
| 第 13 代之前 | 12 / 0 / 14,080 | **6 / 6** / 13,927 | 8 / 4 / 13,700 | 10 / 2 / 14,124 | 12 / 0 / 13,717 |
| 第 16 代之前 | 14 / 1 / 13,912 | **7 / 8** / 13,732 | 8 / 7 / 13,596 | 10 / 5 / 13,871 | 13 / 2 / 14,014 |

Push attempt_08 第 6 代前 5 代都保留，但记忆从 6,087 B 涨到 8,563 B（+41%）。原因是数量级：每个测量字典 177 B，一个 generation 条目付出 2 行 + 1 顶层 ≈ 530 B，而基线条目本身只有 333–609 B；同时记忆头部（语义说明约 1.6 KB + exploration 投影 5.6 KB）已固定占 7.2 KB，实际留给实验表的只有约 7 KB。字典内容在真实数据上几乎恒定（`reward_term_calls` 432009/480010、`diagnostic_calls` 0、`nonzero` true，旧回执三个新键全为 `null`），信息量极低。P1 的压力测试只断言 `omitted_experiment_count > 0` 且行身份保留，看不到“省略了多少代”。

计划要求的只是“缺 runtime / 无 term / 零执行 / 实测零”可区分，而不是把整份测量表进记忆。三种替代编码的实测（[report_variant_*.json](./audit_replay/)，monkeypatch 仅用于测量）：去掉 `null` 键只回收 1–2 代；再去掉顶层重复回收到 10 代；每 lane 一个类别 token（`not_available` / `not_executed` / `no_terms` / `terms_not_called` / `executed_zero` / `executed_nonzero`）恢复到 12–13 代，与基线相当。完整字典仍留在同一 trial 的 `runtime_feedback_summary` 与 `public_history.recent_outcomes`，不丢语义。建议：第 10 列改为类别 token 或稀疏字典并删除顶层重复，同时把“保留代数不低于基线 −1”写成真实 ledger 上的回归门（可直接用本次驱动脚本）。这是收益不高的复杂度的实例，应在 P2/P3 用这条记忆生成 A 载荷之前处理。

### 3.2 重放时摘要相等检查把 ledger 续用绑定到 adapter 投影代码（P2 设计约束）

`project_generation_public_history_record` 现在要求 ledger 里的 `public_summary` 与 adapter 当下从回执重建的结果逐字节相等，否则整个会话历史不可消费。这是有意的 fail-closed，对篡改是正确的；但它同时意味着 `project_public_phase_summary` 输出的任何变化（新增字段、数值格式）都会让所有既有会话——包括 P2/P3 计划使用的 c6 与 attempt_08——无法通过作者路径重放。P2 若要给作者新增行为证据，应按计划已有的 L1/L2 思路放在独立的 task-owned 工件（经 `task_evidence`/`task_evidence_hash` 绑定到 phase 回执），而不是扩展 phase summary；或者给 summary 加投影版本并按版本比对。建议把这一约束写进 P2 范围卡，避免 P2 第一次改 summary 时才发现历史会话“全部拒绝”。

### 3.3 小项（不阻断）

- **同一事实三个名字**：`StairCompleteRewardDispatcher.runtime_summary()` 现在同时输出 `dispatcher_calls`/`step_calls`、`declared_term_count`/`reward_term_count`、`term_calls`/`reward_term_calls`。由同一属性计算，暂不会不一致，但 Stair 门用旧名、共享层用新名，是“单源真相”的表面性缺口；后续由 Stair 自己收敛为一套即可。
- **`available` 的含义**：`measurement_summary` 在只有激活记录、没有任何计数时也返回 `status: available`（各计数为 `null`）。与记忆语义串“`not_available` 表示无记录”一致，但读者容易把 `available` 读成“已测量”。建议在语义串里补一句“`available` 只表示存在运行记录，计数为 `null` 即未测”。
- **回执路径绑定**：两个历史 ledger 的 `private_artifacts` 都是服务器绝对路径，`guard_reference_phase_receipt_hash` 把路径一并入 hash，因此绑定回执重放只能在服务器原路径进行；本次也因此在服务器完成。P2/P3 的本地离线工作要像 P0 那样导出原件，这是既有属性，需在范围卡记一笔。
- **测试环境**：`test_runtime_evidence_projection.py` 未插入 `src` 路径（本仓库 141 个单元测试中 47 个如此），Linux 上需 `PYTHONPATH=src`；不是 P1 偏差，仅供服务器复跑时注意。
- **第三任务测试分工**：`fixture_orbit_tracking` 走的是 round 记录 fixture，generation 路径的非 Stair/Push 覆盖由集成测试的 `_Assembly` 承担；两处合起来满足验收，但分散在两个文件，验收文档已如实说明。

## 4. 过度复杂化评估

P1 的生产改动很小（净 +198 行），没有新增服务、数据库、事件总线或通用词表；三处修复都落在所有权交界（回执→投影、producer→归一化、共享 builder→任务投影），符合计划“只在反例证明的层修”。deepcopy 是必要的：两个已发布 adapter 本来就复制输入（Stair deepcopy、Push 浅拷贝），但共享层的身份比较对任何原地修改的 adapter 都是空转，修复让检查真正生效。唯一“为完整而加”的是 3.1 的测量列，其成本没有在真实数据上度量。文档量相对代码偏大，但相互一致、无夸大（“真实文件形式的 fixture 回执”“未请求模型”等限定都准确）。

## 7. 审计方更正（2026-09-23，修复轮复核时补记）
